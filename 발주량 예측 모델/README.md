# D+3 발주량 예측 — audited_v3 (연구) · audited_v2 (서비스)

가이드북의 일별 최종 ERP 발주 계획량을 달력 3일 앞서 예측합니다. 일별 마지막 로그 이후 사용하며 실측 소비량·재고 최적화 모델은 아닙니다.

**서비스와 대시보드는 아직 audited_v2 모델을 사용합니다.** audited_v3는 v2 평가의 데이터 정렬 오류를 바로잡은 연구 결과이며, 아래 결론에 따라 v2의 정책(7일 이동평균 기본 / LSTM 보조)은 더 이상 근거가 없습니다. 서비스 교체는 별도로 결정합니다.

## audited_v3에서 바로잡은 것

원본 로그를 날짜별로 비교하면 관측일 49일 중 17일은 **전날 스냅숏이 수량 82개 칸까지 그대로 반복된 기록**입니다(추석 9/18~26, 대부분의 주말, 10/11 대체공휴일). 저장 시각(`CRET_TIME`)만 새 날짜이고, `D일`·`D+k일` 열은 여전히 마지막으로 갱신된 날을 기준으로 합니다. 10/31은 로그가 없습니다.

audited_v2는 이 기록을 그날 새로 작성된 계획으로 읽었습니다. 그 결과 두 가지가 틀어졌습니다.

- **기존 D+3 계획 기준선이 엉뚱한 날을 가리켰습니다.** 예: 10/9~11 기록은 10/8 계획의 복사본이라 `D+3` 칸이 10/11(휴일)의 계획입니다. 10/12~14 목표일의 기존 계획이 거의 0으로 비교됐습니다.
- **복사된 수량이 정답으로 쓰였습니다.** 일요일·휴일의 "실제값"이 직전 영업일 값의 복사본입니다.

v2의 "7일 이동평균이 기존 계획보다 MAE 36.7% 낮음"은 이 두 문제에서 생긴 결과입니다.

`demand_contract.load_daily(carryover='realign')`의 처리 규칙은 다음과 같습니다.

1. 전날과 공통 부품의 90% 이상이 82개 칸 모두 같으면 이월일로 표시합니다. 그날과 전날만 보므로 미래 정보를 쓰지 않습니다. 주말이라도 실제로 갱신된 10/2·10/16은 이월일이 아닙니다.
2. 로그가 없는 날(10/31)은 전날 기록으로 채우고 이월일로 표시합니다.
3. 이월일의 계획 칸은 실제 기준일 기준으로 다시 읽습니다. 기준일 이후 k일이 지났다면 `D+3` 대신 `D+(3+k)` 칸을 씁니다.
4. 이월일의 최종 수량은 알 수 없으므로 **정답으로 쓰지 않습니다.** 최근값·이동평균 기준선도 실제 관측된 최종 수량만으로 계산합니다.

정답으로 쓸 수 있는 날이 32일로 줄어, v2의 분할(외부 3회×4일, 회고 7일)은 성립하지 않습니다. v3는 **외부 CV 2회(10/14~10/21, 7일)와 회고 6일(10/25~11/1)**, 내부 검증 4일, 최소 학습 5일로 평가했습니다. 그 밖의 설계(시간 경계 검사, 내부 검증 후 재적합, 회고 전 선택 고정)는 v2와 같습니다.

## audited_v3 결과

| 방법 | CV MAE | CV RMSE | 회고 MAE | 회고 RMSE |
|---|---:|---:|---:|---:|
| XGBoost | **15.9** | 34.7 | **20.2** | 43.6 |
| 기존 D+3 계획 | 16.2 | **32.0** | 22.3 | **41.2** |
| LightGBM | 17.7 | 42.7 | 20.5 | 43.3 |
| 연관 LightGBM | 17.8 | 39.8 | 21.3 | 44.9 |
| CatBoost | 18.6 | 45.0 | 21.0 | 48.2 |
| LSTM | 22.8 | 42.0 | 20.3 | 43.3 |
| 7일 이동평균 | 30.9 | 63.6 | 33.4 | 70.4 |
| 3일 이동평균 | 36.4 | 79.0 | 32.9 | 71.3 |
| 최근값 | 43.7 | 99.0 | 31.9 | 69.0 |

CV는 111개 부품·743행, 회고는 109개 부품·643행입니다. 13개 시험 목표일을 날짜 단위로 재표본화해 기존 계획과 비교했습니다([plan_comparison.json](outputs/audited_v3/plan_comparison.json)).

- **이동평균·최근값은 기존 계획보다 확실히 나쁩니다.** 7일 평균은 13일 중 하루도 기존 계획을 이기지 못했습니다. 일평균 MAE가 13.0개 더 크고, 95% 구간은 8.1~19.8입니다.
- **XGBoost는 13일 중 9일 기존 계획보다 정확했지만 확정할 수 없습니다.** 일평균 MAE 차이는 −1.1개이고, 95% 구간 −3.1~+1.0이 0을 포함합니다. RMSE는 기존 계획이 더 작아, 크게 틀리는 날은 XGBoost가 더 크게 틀립니다. 기존 계획을 입력으로 받아 체계적인 과소 계획(편향 −9.4개)을 보정하는 모델로 해석합니다.
- **LSTM은 학습 자료가 적어 불안정했습니다.** 기존 계획보다 나은 날은 13일 중 3일입니다. seed만 바꿔도 fold MAE가 14.8~23.7로 흔들렸습니다(XGBoost 12.4~18.5).
- 시간대 합계 정의로 바꿔도 선택 결과(XGBoost)는 같았습니다.

결론적으로 현재 자료에서는 **기존 D+3 계획이 가장 강한 기준**입니다. 학습형 모델은 그 계획을 소폭 보정하는 후보로만 볼 수 있습니다.

## 재현 순서

`requirements.txt`를 Python 3.12 환경에 설치합니다. 완료된 버전은 덮어쓰지 않으므로 새 실험은 `--version`을 분리합니다.

```powershell
# audited_v3: 이월 기록 정렬 + 축소 분할
python src/retrain_audited.py --version audited_v3 --carryover realign --holdout-days 6 --cv-days 7 --folds 2 --validation-days 4 --min-train-days 5
python src/compare_against_plan.py --version audited_v3
python -m unittest discover -s tests -v
```

옵션 없이 실행하면 audited_v2와 같은 자료·분할을 만듭니다. PyTorch를 불러올 수 없는 환경에서는 `--skip-lstm`으로 나머지 8가지 방법만 비교할 수 있습니다.

서비스 자료(audited_v2) 갱신 순서는 그대로입니다: `src/build_dashboard_assets.py` → `src/train_related_part_model.py` → 루트의 `firestore/build_unified_seed.py` → `scripts/package_runtime.py`. Firebase 업로드는 별도 동작입니다. `train_final.py`, `evaluate_purged.py` 등 이전 학습 스크립트와 purged_v1/final_v3 모델은 과거 실험 자료입니다.

## 실행

통합 앱은 루트 `setup_local.cmd` 후 `start_demo.cmd`로 실행합니다. 8070 포트에서 계정·외부 API 없이 테스트합니다. 연구용 단독 화면은 이 폴더에서 `python app.py`로 실행합니다.

CSV는 동일 부품 3~60일 자료, 최근 3일은 연속이어야 하며 8일 이력을 권장합니다. 미학습 부품은 최근값으로 대체하고, 격리된 두 부품(Part 21·26)은 정정 전까지 예측하지 않습니다. 현재 CSV 추론은 v2 계약이며 이월 기록을 따로 처리하지 않습니다.
