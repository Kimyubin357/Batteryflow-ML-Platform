# D+3 발주량 예측 — audited_v3 (연구·서비스)

가이드북의 일별 최종 ERP 발주 계획량을 달력 3일 앞서 예측합니다. 일별 마지막 로그 이후 사용하며 실측 소비량·재고 최적화 모델은 아닙니다.

**2026-11-05부터 서비스와 대시보드는 audited_v3를 사용합니다.** XGBoost 예측을 기존 D+3 계획과 비교해 보여 주며, 개선은 확정되지 않았다고 표시합니다. audited_v3는 v2 평가의 데이터 정렬 오류를 바로잡은 결과이며, v2의 정책(7일 이동평균 기본 / LSTM 보조)은 철회했습니다.

## audited_v3에서 바로잡은 것

원본 로그를 날짜별로 비교하면 관측일 49일 중 17일은 **공통 부품의 90% 이상에서 수량 82개 칸이 직전 관측일과 동일**합니다(추석 9/18~26, 대부분의 주말, 10/11 대체공휴일). 이 날짜들을 이월 의심일로 분류하고 `D일`·`D+k일` 열의 기준일이 이전 날짜에 머물렀다고 가정해 보정했습니다. 일부 부품은 달랐으며, 원본 제공자가 저장·갱신 방식을 확인해 준 것은 아닙니다. 10/31은 별도로 로그가 없는 날짜입니다.

audited_v2는 이 기록을 그날 새로 작성된 계획으로 읽었습니다. 그 결과 두 가지가 틀어졌습니다.

- **저장 날짜를 기준으로 읽은 D+3 계획이 목표일과 어긋날 수 있었습니다.** 예: 보정 가정에서 10/9~11 기록의 기준일은 10/8이며, 원본 `D+3` 칸은 10/11(휴일)을 가리킵니다. v2에서는 이 값을 10/12~14 목표일의 기존 계획으로 비교했습니다.
- **이월 의심일의 수량이 새로운 정답으로 쓰였습니다.** 해당 날짜의 최종 수량을 별도로 관측했다고 확정할 수 없어 v3 정답에서 제외했습니다.

v2의 "7일 이동평균이 기존 계획보다 MAE 36.7% 낮음"은 이 두 문제에서 생긴 결과입니다.

`demand_contract.load_daily(carryover='realign')`의 처리 규칙은 다음과 같습니다.

1. 전날과 공통 부품의 90% 이상이 82개 칸 모두 같으면 이월일로 표시합니다. 그날과 전날만 보므로 미래 정보를 쓰지 않습니다. 주말이라도 실제로 갱신된 10/2·10/16은 이월일이 아닙니다.
2. 로그가 없는 날(10/31)은 전날 기록으로 채우고 이월일로 표시합니다.
3. 이월일의 계획 칸은 추정 기준일 기준으로 다시 읽습니다. 기준일 이후 k일이 지났다면 `D+3` 대신 `D+(3+k)` 칸을 씁니다.
4. 이월일의 최종 수량은 알 수 없으므로 **정답으로 쓰지 않습니다.** 최근값·이동평균 기준선도 실제 관측된 최종 수량만으로 계산합니다.

정답으로 쓸 수 있는 날이 32일로 줄어, v2의 분할(외부 3회×4일, 회고 7일)은 성립하지 않습니다. v3는 **외부 CV 2회(10/14~10/21, 7일)와 회고 6일(10/25~11/1)**, 내부 검증 4일, 최소 학습 5일로 평가했습니다. 그 밖의 설계(시간 경계 검사, 내부 검증 후 재적합, 회고 전 선택 고정)는 v2와 같습니다.

저장된 `training_plan_v2.json`의 일부 설명 문자열에는 옛 분할이 남아 있습니다. 실제 실행 설정·분할과의 차이는 [v3 학습 기록 정정](outputs/audited_v3/DOCUMENTATION_ERRATA.md)에 명시했습니다. 완료된 학습 원본과 해시는 보존합니다.

## audited_v3 결과

| 방법 | CV 7일 MAE | CV 7일 RMSE | 회고 6일 MAE | 회고 6일 RMSE |
|---|---:|---:|---:|---:|
| XGBoost | **15.9** | 34.7 | **20.2** | 43.6 |
| 기존 D+3 계획 | 16.2 | **32.0** | 22.3 | **41.2** |
| LightGBM | 17.7 | 42.7 | 20.5 | 43.3 |
| 연관 LightGBM | 17.8 | 39.8 | 21.3 | 44.9 |
| CatBoost | 18.6 | 45.0 | 21.0 | 48.2 |
| LSTM | 22.8 | 42.0 | 20.3 | 43.3 |
| 7일 이동평균 | 30.9 | 63.6 | 33.4 | 70.4 |
| 3일 이동평균 | 36.4 | 79.0 | 32.9 | 71.3 |
| 최근값 | 43.7 | 99.0 | 31.9 | 69.0 |

CV는 111개 부품·743행, 회고는 109개 부품·643행입니다. 아래의 승리일수·일평균 차이·신뢰구간은 CV 7일과 회고 6일을 합친 13일에서 날짜별 MAE 차이를 재표본화한 결과입니다. 위 표의 행 단위 합산 MAE와 집계 범위·방식이 다릅니다([plan_comparison.json](outputs/audited_v3/plan_comparison.json)).

- **이동평균·최근값은 기존 계획보다 확실히 나쁩니다.** 7일 평균은 13일 중 하루도 기존 계획을 이기지 못했습니다. 일평균 MAE가 13.0개 더 크고, 95% 구간은 8.1~19.8입니다.
- **XGBoost는 13일 중 9일 기존 계획보다 정확했지만 확정할 수 없습니다.** 일평균 MAE 차이는 −1.1개이고, 95% 구간 −3.1~+1.0이 0을 포함합니다. RMSE는 기존 계획이 더 작아, 크게 틀리는 날은 XGBoost가 더 크게 틀립니다. 기존 계획을 입력으로 받아 체계적인 과소 계획(편향 −9.4개)을 보정하는 모델로 해석합니다.
- **LSTM은 학습 자료가 적어 불안정했습니다.** 기존 계획보다 나은 날은 13일 중 3일입니다. seed만 바꿔도 fold MAE가 14.8~23.7로 흔들렸습니다(XGBoost 12.4~18.5).
- 시간대 합계 정의로 바꿔도 선택 결과(XGBoost)는 같았습니다.

결론적으로 현재 자료에서는 **기존 D+3 계획이 가장 강한 기준**입니다. 학습형 모델은 그 계획을 소폭 보정하는 후보로만 볼 수 있습니다.

## 재현 순서

`requirements.txt`를 Python 3.12 환경에 설치합니다. 완료된 버전은 덮어쓰지 않으므로 새 실험은 `--version`을 분리합니다.

```powershell
# audited_v3: 이월 기록 정렬 + 축소 분할
python src/retrain_audited.py --version audited_v3 --carryover realign --holdout-days 6 --cv-days 7 --folds 2 --validation-days 4 --min-train-days 5
python src/compare_against_plan.py --version audited_v3
python -m unittest discover -s tests -v
```

옵션 없이 실행하면 audited_v2와 같은 자료·분할을 만듭니다. PyTorch를 불러올 수 없는 환경에서는 `--skip-lstm`으로 나머지 8가지 방법만 비교할 수 있습니다.

서비스 자료 갱신 순서: `src/build_dashboard_assets.py` → `src/train_related_part_model.py` → 루트의 `firestore/build_unified_seed.py` → `scripts/package_runtime.py` → `scripts/package_demand_evidence.py`. 서비스가 쓰는 버전과 모델 조합은 `src/service_policy.py` 한 곳에서 정합니다. Firebase 업로드는 별도 동작입니다. 이 명령은 산출물을 변경하므로 이번 문서 정리에서는 실행하지 않았습니다. `train_final.py`, `evaluate_purged.py` 등 이전 학습 스크립트와 purged_v1/final_v3 모델은 과거 실험 자료입니다.

## 실행

통합 앱은 루트 `setup_local.cmd` 후 `start_demo.cmd`로 실행합니다. 8070 포트에서 계정·외부 API 없이 테스트합니다. 현재 저장소는 통합 앱을 실행 기준으로 사용합니다.

CSV는 동일 부품 3~60일 자료, 최근 3일은 연속이어야 하며 8일 이력을 권장합니다. 현재 audited_v3 고정 모델을 사용합니다. 각 수량은 행의 `date`를 기준으로 **미리 날짜 정렬한 값**이어야 합니다. 선택 열 `carryover_days`는 추정 계획 기준일부터 지난 0 이상의 정수 일수이며, 이월 수량의 관측 여부를 구분하는 데 사용합니다. 이 열만 추가해 원본 계획 열이 자동 재정렬되지는 않습니다. 미학습 부품은 최근값으로 대체하고, Part 21·26은 정정 전까지 예측하지 않습니다.

## 한계

- 시험 목표일이 13일뿐이라 XGBoost와 기존 계획의 차이를 판정할 수 없습니다.
- 회고 6일은 이전 실험에서 이미 본 기간이므로 독립 시험이 아닙니다.
- 이월 판정 기준(90%)은 이 자료의 패턴에서 정한 규칙입니다. 원본 제공자의 운영 기록으로 확인한 것은 아닙니다.
- 새 기간 자료 없이 현장 성능을 확정할 수 없습니다.
- CSV 사전 검사는 `carryover_days`의 유효성을 모두 검사하지 않습니다. 입력 계약에 맞게 확인해야 하며 이 검사 보완은 아직 적용하지 않았습니다.
- 연속 이틀 이상 로그가 없는 경우의 보간 결함은 미수정입니다. 현재 원본의 공백은 10/31 하루여서 저장된 v3 평가에는 해당 조건이 없습니다.
- 서비스 계획 이력에는 이월·보간 표지가 전달되지 않아 표시 날짜를 새 관측일로 단정할 수 없습니다. 이 표시 보완과 CSV 결과의 중복 비교 줄 수정, Copilot 새 근거의 라이브 배포는 보류 상태입니다.
